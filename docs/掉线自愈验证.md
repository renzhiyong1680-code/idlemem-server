# 掉线自愈验证

这份文档记录一次**真实跑出来的**节点掉线与分片迁移，包含完整命令、原始输出和结论。里面的数字来自 2026-11-09 的单机三节点实测，不是设计预期值。

## 前提

- 三节点已起：`powershell -ExecutionPolicy Bypass -File scripts\quickstart.ps1 -BuildLocal -Nodes 3 -Force`
- 至少有一个**双副本**订单（单副本订单在节点掉线后没有可接手的副本，只会变成 `lost`，测不出自愈）：

```powershell
$cfg = Get-Content quickstart\config.json -Raw | ConvertFrom-Json
$h = @{ Authorization = "Bearer " + $cfg.admin_token; "Content-Type" = "application/json" }
$tenant = (Invoke-RestMethod http://127.0.0.1:8080/api/v1/tenants -Headers $h)[0].id
Invoke-RestMethod http://127.0.0.1:8080/api/v1/orders -Method Post -Headers $h -Body (@{
  tenant_id = $tenant; capacity_bytes = 2147483648; replicas = 2; expire_hours = 24
} | ConvertTo-Json)
```

双副本订单会在两个不同节点上各放一个同 `key_prefix` 的分片副本，`GET /api/v1/shard` 能看到两条记录指向同一个 `key_prefix`。

## 步骤

1. 找到要杀的节点里承载的分片与它的进程号：

```powershell
$cfg = Get-Content quickstart\config.json -Raw | ConvertFrom-Json
(Invoke-RestMethod http://127.0.0.1:8080/api/v1/shard -Headers @{ Authorization = "Bearer " + $cfg.admin_token }) |
  Select-Object id, node_id, status, key_prefix | Format-Table -AutoSize
(Get-NetTCPConnection -State Listen -LocalPort 16381).OwningProcess   # node-2 的 agent pid
```

> 端点是 `/api/v1/shard`（**单数**）。写成 `/api/v1/shards` 会 404。

2. 杀进程并全程计时：

```powershell
python bench\failover.py --api http://127.0.0.1:8080 --token $cfg.admin_token --node-id node-2 --pid <pid> --timeout 100
```

脚本每 0.25 s 轮询一次 `/api/v1/shard` 与 `/api/v1/nodes`，输出 `detected_ms`、`node_offline_ms`、`recovered_ms`、前后分片归属和时间线。

> 别拿"杀完之后立刻查 API"当结果。心跳超时是 30 s，杀掉进程后控制面看到的仍是 `active@node-2`，必须等状态真的变化。

## 实测输出（2026-11-09，node-2 被杀）

被杀前 `node-2` 持有两个双副本分片：`shard-6cf023f318dcfac1`、`shard-f75f73c7678a208e`。

```json
{
  "node_id": "node-2",
  "shards_before": {
    "shard-6cf023f318dcfac1": { "status": "active", "node_id": "node-2" },
    "shard-f75f73c7678a208e": { "status": "active", "node_id": "node-2" }
  },
  "shards_after": {
    "shard-6cf023f318dcfac1": { "status": "active", "node_id": "node-1" },
    "shard-f75f73c7678a208e": { "status": "active", "node_id": "node-1" }
  },
  "detected_ms": 34274,
  "recovered_ms": 34274,
  "node_offline_ms": 34274,
  "timeline": [
    { "t_ms": 168,   "states": { "shard-6cf023f318dcfac1": "active@node-2", "shard-f75f73c7678a208e": "active@node-2" }, "node_status": "online" },
    { "t_ms": 34422, "states": { "shard-6cf023f318dcfac1": "active@node-1", "shard-f75f73c7678a208e": "active@node-1" }, "node_status": "offline" }
  ]
}
```

解读：

- **34.3 s 从杀进程到分片在新节点上 `active`**，其中 30 s 是心跳超时（`interval` 默认 10 s、超时 3 次判死），剩下 4 s 是调度器一轮 tick 与写库；
- 期间 `node-2` 被判 `offline`，两个分片的所有权改判给 `node-1`，没有出现 `lost`（因为它们是双副本订单，另一份副本本来就在 `node-1`）；
- 客户端在这 34 s 里打到 `node-2` 的请求会失败，超时后重连到在线的节点即可继续读写。

## 已知边界（别对外说过头）

- **只救可用性，不救数据**。kvstore 是纯内存实现，迁移是重排分片所有权，不搬运键值；被杀节点内存里的键在迁移后读不到（`GET` 返回空）。持久化与副本同步属于后续阶段，当前版本不提供。
- **单副本订单救不回来**。`replicas=1` 的订单在所属节点掉线后没有副本可接管，分片会进入 `lost`，需要客户重新下单/重新写入。
- **自愈不重启进程**。脚本只把分片改判到活着的节点，死掉的 agent 需要自己重新拉起（带原来的 `-id`），否则该节点会一直是 `offline`。
- **刚恢复的节点不会立刻接到新分片**。实测中 `node-3` 重启上线后新建的双副本订单只落在 `node-1` / `node-2`，新分片分配对刚掉过线的节点偏保守——这是调度侧的现状，不是 bug，但会影响"扩容即生效"的观感。
